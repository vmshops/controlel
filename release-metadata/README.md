release-metadata/ README

Purpose
-------
This folder contains the repository-owned canonical release metadata used to
generate human-facing release pages, draft release notes, and to serve as the
single source of truth for release-level facts.

Schema
------
- metadata_version: integer (current: 1)
- releases: list of release entries

Release entry fields (schema v1)
- release_id: unique identifier (string)
- component: "core" | "home_assistant" | other (string)
- title: human title (string)
- version: semver-like string
- status: "published" | "candidate" | "pretag" | "draft"
- tag: annotated git tag name (string) or null for non-tagged releases
- commit_sha: 40-char commit SHA or null if not recorded here
- tagged_at: ISO 8601 git tag object timestamp (tagger date) for tag-bound releases; do not use this as external publication time
- published_at: ISO 8601 time the first immutable public artifact became available
- provenance: tag/object binding and public-byte verification method for a published core release
- artifacts: published filename, byte size, SHA-256, and per-file upload timestamp
- summary: short human summary
- highlights: list of short bullets
- compatibility: mapping of compatibility facts (HA version, required_core, python)
- notes: freeform list of notes

Guidelines
----------
- Avoid embedding local artifact paths or mutable build output. Published
  artifact hashes and sizes are copied here only after verification against the
  canonical provenance manifest generated by
  `scripts/packaging/prepare_final_core_release.py`.
- Fields marked "human-authored" should be written by a release manager when
  preparing a release. Automation may fill artifact and provenance fields after
  a canonical build.

Human-authored vs generated
- Human-authored: title, summary, highlights, compatibility (high-level), notes
- Generated/verified at publication time: published_at, provenance identity,
  artifact filenames, hashes, sizes, and upload timestamps

How to use
----------
- Release automation reads releases.yaml to produce draft release notes, docs
  pages, and to populate templates. After a canonical build, release automation
  updates provenance and may update releases.yaml (or write a companion
  provenance record) and open a docs PR for review.
