# Home Assistant entity reference

This is the authoritative quick reference for every public Home Assistant
entity exposed by Controlel integration 0.10.0. Entity IDs are generated by
Home Assistant and may be renamed by users. The stable registry unique ID is
`<config_entry_id>_<key>`; the heating-performance key is
`heating_performance_<zone_id>`. Examples below therefore use descriptor keys,
not user-generated `entity_id` strings.

All entities are read-only projections. In the **Control** column, **YES** means
the underlying value participates in or represents control semantics; changing
the entity itself is impossible and it is never a control input. **NO** means
presentation/diagnostics only. All entities exist in Basic, Detailed, and Debug
profiles. Profile changes affect refresh cadence and the attributes explicitly
noted below, never entity identity or control. `Unavailable` means evidence or
an active deadline is absent; it must not be read as `false` or `disabled`.

## Truthfulness rules

- A requested command is not a successful command.
- A successful service call is dispatch evidence, not reported device state.
- Reported source `enabled` is controller feedback, not proof that a burner is
  firing or physical heat is being produced.
- `unknown`, `unavailable`, `indeterminate`, and null are not `disabled` or
  false.
- Supervisor `failsafe` means the host process is alive and the guarded
  failsafe runtime owns commands. It does not describe complete Home Assistant,
  OS, power, network, or hardware failure.
- Commanded actuator target/position/open state and reported actuator state are
  separate evidence. Neither implies physical heat delivery.

## 1. Quick troubleshooting index

| Question | Check first | Then inspect |
|---|---|---|
| Why is heating ON? | `heat_demand`, `confirmed_zone_heat_demand`, `last_requested_command`, `last_command_outcome` | `raw_heat_demand`, `hysteresis_demand`, `active_demand_cause`, diagnostics-only `source_resilience` |
| Why is heating OFF? | `heat_demand`, `safety_state`, `last_requested_command`, `last_command_outcome` | `measurement_status`, `timeout_action`, `source_control_state` |
| Why has the source not switched yet? | `source_control_state`, `active_lockout_type`, `active_lockout_remaining`, `deferred_command` | `earliest_next_enable_time`, `earliest_next_disable_time`, diagnostics-only recovery/reconciliation fields |
| Did an external/manual source state change occur? | Download diagnostics: `source_resilience.reported_source_state`, `reported_source_observed_at`, `transition_history` | `desired_source_state`, reconciliation status/reason; no standalone reported-source entity exists |
| Is reconciliation active? | Download diagnostics: `source_resilience.reconciliation_status`, `reconciliation_reason`, `drift_detected` | corrective intent, blocked reason, and blocked deadline |
| Is the runtime in failsafe? | Download diagnostics: `runtime_supervision.supervisor_state`, `command_authority`, `failsafe_state` | `runtime_status`, `fatal_failure`, normalized fatal cause and restart fields |
| Did the normal runtime crash? | `fatal_failure`, `runtime_status` | Download diagnostics: `last_fatal_cause_code`, generation and restart campaign |
| Is a restart attempt pending? | Download diagnostics: `next_restart_at`, `restart_attempt_count`, `restart_budget_exhausted` | supervisor state and command authority |
| Is temperature stale? | `measurement_status`, `measurement_age`, `measurement_stale_deadline` | `measurement_stale_remaining`, `latest_input_status` |
| Is anti-cycling/minimum ON/OFF blocking? | `active_lockout_type`, `active_lockout_deadline`, `active_lockout_remaining` | `deferred_command`, `deferred_reason`, passive earliest-next boundaries |

## Shared state vocabulary

- Demand: `heat_required`, `no_heat_required`, `indeterminate`.
- Measurement: `valid`, `unavailable`, `unknown`, `invalid_value`, `stale`,
  `future_timestamp`, `not_received`.
- Runtime: `starting`, `active`, `stopped`, `fatal_error`.
- Safety: `normal`, `indeterminate_grace`, `timeout_action_applied`, `stopped`,
  `fatal_error`.
- Confirmation: `no_heat_required`, `confirmation_pending`,
  `heat_required_confirmed`, `indeterminate`, `stopped`, `fatal_error`.
- Command outcome: `none`, `dispatched`, `suppressed_duplicate`,
  `suppressed`, `deferred`, `held`, `failed_recoverable`, `failed_fatal`.
- Binary sensors use Home Assistant `on`/`off`; when unavailable, that is
  unknown evidence rather than `off`. Their translated UI/history display is
  **Yes/No** in English; a future Czech translation can provide **Ano/Ne**
  without changing raw state, entity identity, or automations.

### Binary presentation contract

All public binary entities express factual propositions, rather than device
power state. Home Assistant stores and exposes raw `on`/`off` for automations;
the entity translation presents those values as **Yes/No** to users.

## 7. Source reconciliation and resilience

M30.2 source evidence is **diagnostics-only** under downloaded diagnostics key
`source_resilience`; no standalone HA entities are created. The bounded schema
contains: `schema_version`, `updated_at`, `operating_mode`,
`operating_mode_reason`, `desired_source_state`, `reported_source_state`,
`reported_source_observed_at`, `last_successful_command`, `source_ownership`,
`source_capabilities`, `drift_detected`, `reconciliation_status`,
`reconciliation_reason`, `transition_history`, `recovery_status`,
`recovery_reason`, `corrective_intent_pending`,
`corrective_action_blocked_reason`, `corrective_action_blocked_deadline`,
`manual_recovery_active`, `manual_recovery_deadline`,
`manual_recovery_remaining_seconds`, `safe_heating_degraded`, and
`water_target_intent`.

These fields change only when current demand, explicit reported source evidence,
operating mode, recovery, or deterministic deadlines change. They represent
control semantics (**YES**) but their diagnostic projection is passive. A
Controlel-owned mismatch with unknown transition age can remain held for five
minutes. `corrective_intent_pending` is intent, successful command is dispatch
evidence, and `reported_source_state` is explicit HA device evidence; none is
physical burner confirmation. Null/unknown remains unknown.

## 8. Runtime supervision and failsafe

M30.2D supervision is **diagnostics-only** under `runtime_supervision`. Fields
are `schema_version`, `supervisor_state`, `command_authority`,
`normal_runtime_generation`, `last_fatal_cause_code`, `failsafe_state`,
`failsafe_reason`, `restart_attempt_count`, `restart_budget`, `next_restart_at`,
`restart_budget_exhausted`, `manual_recovery_deadline`,
`last_successful_recovery_to_normal`, and the adapter-added
`reported_source_state`.

These values represent control authority (**YES**) and change on fatal normal
runtime failure, generation quarantine, failsafe takeover, restart attempts,
manual recovery, successful handover, or reported-source events. They are
bounded stable codes, not arbitrary exception messages. `command_authority`
distinguishes `normal` from `failsafe`; failsafe authority is exclusive. It
does not claim that Home Assistant, the OS, power, or hardware can be supervised
after their process boundary is lost.

## 9. Heat delivery

Heat delivery is **diagnostics-only** under the downloaded `heat_delivery`
array; no standalone actuator entity is created. Each bounded item exposes
actuator/zone identity, mode, ownership, capabilities, assist policy/activity,
zone target and measurement, normal/commanded/reported actuator values, last
requested command, last successful command, outcome/timestamp, and normalized
failure evidence. The underlying source is `HeatDeliveryState`; changes come
from confirmed demand, accepted measurements, explicit actuator reports, and
adapter command outcomes. These fields represent control semantics (**YES**).

Requested target, position, binary-open, and remote-temperature values remain
separate from reported values. Successful dispatch never fabricates a report
or physical valve/heat state.

## 12. Version and configuration diagnostics

<!-- entity:sensor:integration_version -->
| Entity key | Platform/type | Purpose and exact meaning | Values | Source / what changes it | Control | Profile / attributes / warnings |
|---|---|---|---|---|---|---|
| `integration_version` | Diagnostic text sensor | Installed Controlel HA integration version. | Version string | Literal `INTEGRATION_VERSION`; changes only on integration upgrade. | NO | Always present. Device `sw_version` uses this string and is never a list. |
<!-- entity:sensor:core_version -->
| `core_version` | Diagnostic text sensor | Installed public Python core distribution version. | Version string | One executor-offloaded `importlib.metadata.version("controlel")` lookup during setup, then retained in the snapshot. | NO | Always present; no repeated metadata filesystem lookup. |

Downloaded diagnostics additionally expose **diagnostics-only**:

- `configuration`: normalized effective values used to compose the runtime;
- `configuration_provenance`: allowlisted legacy data/options, normalized
  effective values, user-facing timing units, and precedence source;
- `versions`, bounded `operational_snapshot`, bounded `decision_trace`,
  `observability`, bounded `operational_events`, counters, entity IDs, and
  normalized active issue IDs. `operational_events` has schema version 1,
  capacity 200, total/retained/dropped metadata, latest event time, and ordered
  localization-neutral semantic event records.

Unknown config-entry keys, secrets, arbitrary service payloads, arbitrary
exception messages, raw sample history, and physical-state claims are excluded.
The diagnostics projection is passive (**NO**) even when a field describes
underlying control semantics.

M31A adds no entity key or unique ID. Operational events are available only in
downloaded diagnostics; unload discards the in-memory stream and reload starts
a fresh runtime stream rather than fabricating continuity.
